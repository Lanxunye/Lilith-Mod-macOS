# QQ 统一交流状态与决策预览

2026-10-24，开发预览。沿用现有 Companion、DeepSeek 对话核心和 NapCat / OneBot；不另起一个会同时回复的聊天代理。基础角色卡 `character/lilith.json` 不变。默认 `mind_mode=observe`。部署或切换状态模式不会解除暂停，也不会开启群聊、随机参与、搜索或主人表情库许可。

## 三个参考项目如何组合

| 参考 | 借鉴的结构 | 本项目实现 |
| --- | --- | --- |
| [Derpyu520/qq-bridge](https://github.com/Derpyu520/qq-bridge) | 参与判断、等待与实际发送分开；角色与协议规则分开 | 沿用现有 reply / wait / skip、有限等待和统一发送出口，新增状态预检、发送前边界复核；只有平台回执确认后记为实际互动 |
| [flyinstar/dsh-qq-bridge](https://github.com/flyinstar/dsh-qq-bridge) | 稳定 PERSONA 与语境 STYLE 分层，按会话和成员检索记忆 | 原角色卡固定；启用状态层后才附加本轮表达提示；计划、约定等只从本群当前成员已有事实中取出，保留证据与来源 |
| [nanbengxian-cyber/dafeiyu-qq-bot](https://github.com/nanbengxian-cyber/dafeiyu-qq-bot) | 独立状态汇总、冲突观察、成员关系与明确的少打扰边界 | 心情、交流余量、话题参与度、成员熟悉度、约定线索合并为快照；默认观察提案与建议的差异；按群和稳定成员账号隔离 |

这是按结构独立编写的 Node.js 实现，没有复制上述项目源码或角色卡。nanbeng 仓库中的部分 `dsh-*` 插件基于 AstrBot，不能直接当 DeepSeek Harness 插件装入本项目；也没有引入 AstrBot、SnowLuma 或其插件依赖。QQ 对话继续使用当前统一核心，不继承桌面 DSH 的文件及系统工具权限。

## 模式和处理顺序

- `off`：不采集本层信号、不记本层决策，保留已存状态。仍遵守现有暂停、白名单、表情许可和每日额度。
- `observe`：记录派生状态和决策建议；发送行为沿用现有参与提案，不向对话提示词注入新状态。适合先比较，不等于自动开启聊天。
- `active`：将快照提供给参与判定和本轮表达；少打扰、低交流余量可阻止普通插话。明确 @、引用本群莉莉丝或直接称呼仍优先回应；明确要求“不要回复这条”则略过本条。

消息通过账号与范围检查后，才进行本层观察；收集模式在此前返回，不进入观察或对话。普通消息先做状态预检，再按需请求参与判定。最终行动接受全局暂停、仅收集、白名单和所有群合计 100 条/天的约束。发送前再次检查成员边界与现有话题时效。未知回执仍按现有规则暂停，不自动重发，也不增加熟悉度。

## 状态的含义和限制

这些是解释本轮表达与参与的派生标签，不是心理诊断或真实情绪测量。

- 心情只取明确向莉莉丝表达的感谢、困惑或难过等信号，约 15 分钟后恢复平静；成功发送不会延长这段状态。情绪附带来源成员，只在回应对应成员时应用，避免将一人的难过误当成下一人的感受。
- 交流余量只在确认发送后降低，半衰恢复时间为一小时。低余量只抑制普通插话，明确问题仍正常、完整回答。
- 话题参与度来自已经发送的同话题互动，并逐步回到中性；话题由现有机制决定是否失活。它作为参考输入，不伪装成模型推断出的永久兴趣爱好。
- 熟悉度按机器人、群、成员稳定账号隔离；改名、同名不会合并。明确感谢每天最多累计 10 点，约 30 天半衰；辱骂、他人转述或沉默不会机械扣分。熟悉度只影响表达，不改变权限、事实标准和回答质量。
- 成员直接说“莉莉丝，请别打扰我了”等明确请求，可建立 24 小时少打扰边界；不把普通含混语句当指令。“不要回复这条”只约束本条。
- 成员可明确要求停止记录关系，也可在本机控制台管理。退出会清除本层该成员关系计数、信号和可关联决策，保留退出标记；后续不累计该成员关系。此操作不等于清除已有聊天档案或长期事实，后者仍由原有记忆管理负责。
- 清空或重写全局长期记忆时，本层派生状态与熟悉度也一同清除；明确设置的少打扰期限和退出标记继续保留，避免遗忘操作意外恢复主动打扰。普通聊天上下文重置仍按原行为保留长期事实及成员边界。
- 计划、约定、待办和提醒都是有来源的记忆线索，标记 `memory_lead_not_scheduled`，不会创建日程、执行任务或主动兑现承诺。不得声称已经安排或完成。
- 严肃求助和故障分析优先完整文字，不用表情替代回答。表情仍须来自当前范围允许的候选列表，并遵守连续斗图及发送额度限制。

## 控制台和本机接口

在 WebUI 的“QQ 桥接”内：

1. “群聊参与与节奏”选择统一交流状态的模式，再保存 QQ 配置。它与回复开关独立。
2. 展开“统一交流状态与只读预演”，填写白名单范围与成员，输入模拟文字和参与提案。
3. 点击“仅预演，不发送”。此过程不调用模型、不保存模拟文字、不写观察状态、不发 QQ；展示建议与实际硬门槛。暂停时 `effective.action` 仍为 `skip`。
4. 如需管理真实成员边界，选择下方操作并点击“保存成员边界”。预演按钮不会替你保存边界。

本机端点全部要求已有的 Bearer 认证：

- `GET /v1/qq/mind`：快照与最近决策原因；决策审计不含原始聊天或图片。
- `POST /v1/qq/mind/preview`：只读预演；字段 `scope`、`member`、`text`、`force` 和 `proposal.action`；文本最多 2000 字符。采用实际每日额度，不接受传入值放宽限额。
- `POST /v1/qq/mind/member`：管理同范围的成员；`action` 为 `quiet`、`resume`、`opt_out`、`opt_in` 或 `reset`。重置熟悉度保留已有退出选择。

状态存在原私有 SQLite 的 `qq_mind_*` 表。决策审计最多保留 1000 条；信号和每日累计记录清理 90 天前的数据。预演不写这些表。状态读取失败时，启用模式会停止普通插话；明确问题仍走原对话逻辑。所有 API Key 与原始图片继续留在私有数据目录，不进入公开源码。

## 验证边界

新增离线测试覆盖模式差异、事件重放、按日累计与衰减、成员和群隔离、明确边界、退出记录、已确认交付记账、未知回执暂停、来源事实、表情许可、每日额度、认证接口以及只读预演。协议端与参与模型使用本地替身，不向实际 QQ 发送验证消息。

真实群聊的自然程度仍需持续体验验收。本模块不会自动解除暂停或更改收发开关，也不会凭空填充成员人格。联网、绘图、图片识别和语音须分别配置对应服务。

真实对话服务已用三轮虚构成员消息做隔离验证：情绪回应、不同成员的画画计划、确认少打扰请求均通过；修正了复核时发现的情绪/经历跨成员归属问题。验证期间实际 QQ 发信为零。少量样例通过不代表所有语言情境或长期群聊都已验收。
